The challenge

ePlanner houses diverse modules—including Site Simulation, Wind Analysis, and Urban Synth. Each module was built at different times, by different engineers, and with different UX approaches. This led to inconsistent components, disjointed navigation patterns, and confusing workflows across the platform.

As planning decisions involve policy makers, analysts, and technical specialists, clarity and consistency were essential to reduce cognitive load and improve workflow efficiency.

Design system governance

ePlanner's team had been building on Calcite, Esri's open-source design system. The problem was that Calcite was designed for general GIS tooling, not for ePlanner's specialised custom interfaces. With no shared process for handling gaps, each team solved the same problems independently, resulting in inconsistent components scattered across modules. Thus I came up with a plan to consolidate ePlanner's design system, to ensure it's scalability and consistency across all the tools.

DLS enhancement plan


I led a structured enhancement of the DLS across five workstreams, with the long-term goal of replacing Calcite dependency with a custom Storybook the team owns entirely.

01. Restructured the Figma library

Reorganised the component library to follow Atomic Design principles, replacing a flat, hard-to-navigate structure with intuitive categories including Templates, Navigation, Cards, and Patterns.

02. Tidied existing Calcite components

Audited and cleaned Calcite components to better fit ePlanner's use cases. Removed unused variants, simplified prop sets, and brought component structures in line with how the platform actually uses them.

03. Built new custom components

Designed ePlanner-specific components that fall outside Calcite's scope entirely, including Notice Banners, Button Group (Round), ePlanner Navigation, Workspace Card, and Content Display. Each follows consistent patterns for use across all tools.

04. Adding documentation

Added usage guidelines, anatomy breakdowns, spacing rules, and contextual examples for all updated and new components. These docs serve as the blueprint for the eventual Storybook transition.

05. Established shared design patterns

Beyond individual components, I reviewed tools across ePlanner and defined fixed interaction patterns to ensure consistent behaviour across all modules — covering panel layouts, left panel interactions, tool-switching flows, and AI-assisted features like Image Generation.

06. Documenting inconsistencies to be fixed

I also noted down any inconsistencies in existing interactions, and ensured alignment with both the design and development teams on the new consistent interaction to be used moving forward.


With the Design Sytem overhaul, we saw a huge improvement in the visual design and consistency across the entirety of ePlanner. The developers across different feature teams were also able to rely on the new design system to build their new features independently of the main design team.

RBAC: Access management for ePlanner

ePlanner's datasets carry varying levels of sensitivity. Different government agencies and user groups need access to different datasets, and that access has to be managed, audited, and kept current. Before RBAC, this was handled manually and inconsistently — admins had no structured way to assign access at scale, users had no visibility into what they could access or why, and group owners were fielding ad hoc requests with no centralised tool to manage them.

RBAC is a standalone access management system built alongside ePlanner to solve this. It serves four distinct user roles, each with meaningfully different needs, and handles two core flows: automated access assignment through Standing Orders, and manual access through user-initiated requests.

Admin

Creates and manages groups, submits Standing Order requests for automated agency-based assignment, monitors onboarding metrics, and handles new agency domains flagged by the system.

Manager

Reviews and approves or rejects Admin's Standing Order requests, with access to supporting evidence and the ability to request modifications before making a final decision.

Group Owner

Reviews individual access requests for groups they own, approves or denies with comments, can bulk-action multiple requests, set approval delegates, and view request history.

User

Requests access to groups from within ePlanner or directly via RBAC, tracks request status, views current memberships, and receives notifications on approval outcomes.

Standing Orders: automated assignment

The core challenge for admins was scaling access management across agencies. Manually adding individual users was unsustainable as ePlanner grew. Standing Orders solve this by letting admins define rules. For example, any user whose agency matches "URA" is automatically assigned to the URA group on first login. The flow required careful design to handle edge cases: what happens when an agency is new and has no existing Standing Order, when a Manager rejects an Admin's request, or when a user logs in for the first time from an unknown domain.

User Requests: self-serve access

Users can also discover datasets they need access to, either from within ePlanner directly or by browsing RBAC's group directory, and submit a request. The design challenge here was the form complexity. A single user request for multiple groups generates separate requests to each group owner, each of whom acts independently. Users needed clear visibility into the status of each request without the interface becoming overwhelming. Group owners needed to be able to act quickly across multiple pending requests without losing context on who was requesting what and why.

Design system used

ANT Design, chosen to handle the complex, form-heavy workflows that ePlanner's Calcite system was not suited for.

Users served

1,000+ government agency users across Singapore's whole-of-government ePlanner deployment.

Key pain points addressed

Manual, unscalable access assignment; no user visibility into access status; fragmented group owner workflows with no centralised review tool.

Key design challenges

Four roles with distinct mental models sharing one system; branching approval logic with rejection, modification, and re-submission flows; cross-system handoff between ePlanner and RBAC.

Establishing a research practice

When I joined, there was no formalised user research or testing process. Design decisions were largely driven by internal assumptions and ad hoc feedback. I introduced a structured UX research framework, one the team could own and repeat without needing a dedicated researcher, with customisable templates for planning sessions, capturing findings, and translating insights into actionable design decisions.

The impact was immediate: 9 moderated usability sessions across 7 features, 16+ key insights surfaced, and for the first time, prioritisation decisions could be backed by direct user evidence rather than stakeholder opinion alone.
